Tour Detail Page — Architecture Approaches

How should the extended tour schema and detail page be structured?

A

Single Enriched JSON + Monolithic Page

Extend tours.json in-place with all new fields. One large JSON file holds everything. The detail page ([slug].tsx) is a single component that renders all sections inline.

Pros

  • Simplest — one file, one page component
  • No new data architecture to learn
  • Easy to reason about data flow

Cons

  • tours.json becomes very large (~2000+ lines)
  • Page component becomes monolithic
  • Tour listing pages load full detail data they don't need
B

Split JSON (Summary + Detail) + Sectioned Components

Keep tours.json as a lightweight summary (cards/listings). Add tours-detail.json with full content keyed by slug. The detail page composes focused section components (Hero, Itinerary, Pricing, Included, etc.).

Pros

  • Listing pages stay fast — only load summary data
  • Detail data is isolated and manageable
  • Section components are reusable and testable
  • Clean separation of concerns

Cons

  • Two files to maintain per data change
  • Must keep summary and detail in sync (same slugs/ids)
C

Per-Tour JSON Files + Sectioned Components

Each tour gets its own file: tours/ba-ho-waterfall.json, tours/1d-nha-trang-to-dalat.json, etc. A lightweight index (tours-index.json) lists slugs + summary fields for listings. Detail page uses the same sectioned components as B.

Pros

  • Each tour file is self-contained and easy to edit
  • Adding a new tour = adding one file + one index entry
  • No giant JSON files

Cons

  • More files to manage (7+ individual JSONs + index)
  • Overkill for 7 tours — adds complexity without clear benefit at this scale
  • Bigger departure from current architecture

⭐ Recommendation: B

Split JSON with sectioned components strikes the best balance. The listing pages stay lean, the detail data is cleanly isolated, and section components (TourHero, TourItinerary, TourPricing, etc.) keep the page maintainable. With only 7 tours, two well-organized JSON files are easy to manage and don't require the per-file overhead of option C.
